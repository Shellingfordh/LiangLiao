# 无感联机入口与 LLM 中继设计

日期：2026-09-27  
状态：已确认设计，待实施  
范围：为「送给你这个回来的人」启用 Maker 联机服务端中继时，保持冷启动体验与现有单机版本一致。

## 1. 目标与边界

玩家打开游戏时，不能看见 Maker 的默认大厅、匹配、房间列表或等待他人的界面。联机只是获得服务端 LLM 润色能力的基础设施；产品仍是一个人的陪伴体验。

- 冷启动先呈现角色状态窗的原创静帧与轻量过渡。
- 后台自动创建只含当前玩家的房间，成功后进入现有聊天和 3D 状态窗。
- 连接失败或 8 秒无结果时，仍进入同一游戏内容，但关闭 LLM 中继、回复回落本地 Lua 模板。
- 不实现陌生人匹配、房间浏览、邀请、聊天或多人玩法。
- 3D 人物、场景、存档和生活状态仍完全在客户端；本次不改模型资产管线。

## 2. 入口架构

开启 `@runtime.multiplayer.enabled` 后，配置 `multiplayer.lobby_runtime` 指向项目自建入口。不要使用或换皮内置五屏大厅。

```
lobby_runtime
  ├─ 自动创建单人房 → StartGame → 联机客户端入口
  │                                  └─ ClientGameRuntime.Start("online")
  │                                      └─ LLM relay 可用
  └─ 失败/超时 ────────────────────────└─ ClientGameRuntime.Start("offline")
                                         └─ LLM relay 明确关闭
```

把当前 `main.lua` 中客户端启动、停止和单帧调度整理为可复用的客户端游戏运行时；联机客户端入口和离线回退都调用它。服务端入口只启动 `scripts/network/Server.lua`，不得初始化 UI、3D、存档或玩法。

这个拆分必须保证只有一个全局 `Update` 订阅方。模块不得自行按函数对象订阅 `Update`；沿用现有 `main.lua` 的全局名字订阅、显式 `Tick(dt)` 调度模型。

## 3. 玩家可见流程

| 状态 | 画面与文案 | 平台动作 | 下一步 |
| --- | --- | --- | --- |
| `connecting` | 现有原创角色静帧淡入；“正在靠近若夕…” | 自动 `CreateRoom` | 已创建后开始游戏 |
| `entering` | “她正在接通”；呼吸光点与平滑进度，不能伪造精确百分比 | `StartGame`，真实进度只作下限 | 引擎切换到联机客户端入口 |
| `online` | 覆盖层淡出，进入原聊天页 | LLM relay 可用 | 正常游戏 |
| `offline` | “信号不太好，先按原来的方式陪你聊” | 不再等待网络 | 进入相同游戏运行时，relay 关闭 |
| `retrying` | 轻提示“再试着接通…” | 再次自动建房/开局 | 成功转 online；失败回 offline |

总连接预算为 8 秒，涵盖建房和连服。失败、超时、被踢和平台异步错误必须有确定收尾，不能露出默认大厅或把玩家困在加载页。离线模式允许用户继续聊天；主动重试是可选增强，不得阻塞现有输入。

加载页只使用已有原创静帧与 `urhox-libs/UI` 的轻量动画；不在 lobby 和正式游戏各启动一份完整 3D 场景。所有主按钮使用 `OnPointerDown`，并显式执行 `button.focusable = false`；条件子树不得在 `props.children` 中留下 `nil` 空洞。

## 4. LLM 中继契约与安全

联机成功后，客户端才把 `scripts/network/Client.lua` 作为 `PolishService` transport 注入；离线、无连接、禁用开关或任何连接失败均不注入 transport。`LlmRelayEnabled` 默认保持 `false`，直到白名单、联机入口和真机验证完成。

服务端只允许向已获 TapTap 精确白名单批准的 URL 出站。当前候选为：

```
https://api.deepseek.com/chat/completions
```

服务端收到 RemoteEvent 时不得信任任意客户端 JSON：必须检查版本、精确字段集、类型、长度、可选引用和允许城市/事件词表；拒绝额外字段、控制字符和超限正文。服务端应尽可能用服务器 UTC 与确定性事件规则重建事实；客户端仍以 `PolishService.ValidateResponse` 与事实词表守卫作为最后一层。

同一 `requestId` 在 5 分钟内必须复用在途结果或已完成结果，不能重复扣预算或请求模型。客户端超时、断线和主动停止时，服务端应取消对应上游请求或在其完成前使其不可交付；上游预算不得晚于玩家已回落的时刻。

模型 Key 不得作为会被提交的源码字面量。实施前必须确认 Maker 服务端可用的安全注入方式；若平台没有该能力，必须先向用户说明风险并使用可撤销、低额度、仅限此 demo 的 Key，不能静默把长期 Key 写进 Git 历史。Key、用户原文、完整私聊和模型输出原文均不进日志。

## 5. 3D 资产兼容性

加载页引用状态窗的已存在原创静帧，不复制角色模型。正式人物继续由客户端 `StatusWindow` 加载；以后换人只需遵循 GLB → MDL/材质/纹理/prefab 的资产流程并更新角色资源引用。每次换人须在真机重验镜头、包围盒、材质、骨骼/动画兼容性与性能；不触及大厅或 LLM 中继。

## 6. 验收

1. 开启联机后，冷启动至进入游戏全程不出现默认大厅、房间列表或匹配 UI。
2. 联机成功时，加载覆盖层淡出，现有 3D 状态窗和聊天页正常出现；日志有 `润色 结果=llm`。
3. 断网、建房失败、连服超时和服务端踢出时，8 秒内进入离线游戏；聊天可用且日志为模板回落，不报未处理 ERROR。
4. 重试成功后只启用一个 relay transport；失败不会重复订阅事件或残留加载 UI。
5. 服务端拒绝非法/重复请求；同一 `requestId` 不重复调用上游。
6. 真机包不含 API Key、上游 Authorization 或服务端模块；真机确认角色渲染和加载动画无回退。

## 7. 实施前置条件

- 用户向 TapTap Maker 申请并获得目标 URL 白名单结果。
- 用户确认可接受“单人联机”作为底层实现，以及本设计的 8 秒离线回退。
- 实施者在修改 Lua 前完整阅读 `engine-docs/lua-scripting-guide.md`、自定义大厅与联网指南，并按项目规则阅读至少三个相关示例。
- 完成后先跑 Lua LSP，随后才进行 Maker 云端构建和真机验证。
