# 《送给你这个回来的人》v2 设计规格

> 日期：2026-09-15
>
> 状态：已确认，待按 PoC 范围实施
>
> 方向赛道建议：游戏（同时申报 Best Use of Tripo；World Labs 为可选工具赛道）

## 1. 产品定义

这是一个聊天优先的 3D 陪伴体验。

用户不是回到一个等待自己的 NPC 小镇，而是与一位生活在另一座真实时区城市的人持续聊天。两人处于同一条真实时间线：用户在北京时间早上发出的消息，可能被生活在洛杉矶傍晚的她在回家路上读到；用户深夜醒着时，她也许刚起床、正在厨房煮咖啡。

她不是随时在线的客服式角色。她有课、工作、朋友、疲惫和不愿立刻回复的时候。用户看到的 3D 状态窗口展示她此刻可感知的生活片段：咖啡馆、通勤路上、公寓或休闲地点。核心礼物是：**世界的另一边，有一个人也在同一个“现在”里生活。**

### 1.1 主题陈述

**送给每一个在夜里给远方发消息的人：你不必立刻被回答，但你的话会抵达一个真实在生活的人。**

### 1.2 成功体验

玩家完成以下链路，即认为 PoC 成功：

1. 创建一段关系，选择前史与她所在城市；
2. 看到她当地时间决定的 3D 场景和状态；
3. 在她无法即时回复时仍能留下消息；
4. 稍后收到一条能解释其延迟、且引用用户消息与她刚经历事件的回复；
5. 在下一次互动中发现她记得这段共同经历。

没有游戏内输赢或剧情结局。技术异常必须被温和降级，而不以“关系失败”打断体验。

## 2. 范围与非目标

### 2.1 首轮 PoC 范围

- 单一、可深度相处的原创女性角色；
- 聊天为主，固定镜头的轻量 3D 状态窗口为辅；
- 四城初始化：上海、成都、洛杉矶、伦敦；
- 四类关系前史：陌生网友（默认）、高中同学、前同事、久未联系的朋友；
- 四类场景：公寓、咖啡馆、通勤、休闲地点；
- 本地时区与角色当地时区、季节、稳定随机天气共同驱动事件；
- 可用性状态、消息排队、一次延迟回复、一次共同记忆回调；
- TapTap Maker 可运行预览与真机测试，Tripo 资产有可追溯来源。

### 2.2 明确不做

- 不接入真实天气、地图、社交平台或新闻；
- 不让用户直接操控角色或在大世界中自由行走；
- 不做多角色切换、多人聊天室、好感度数值面板或恋爱结局；
- 不承诺模型在后台持续运行。离线期间的生活由再次打开时依据时间窗反推；
- 不直接使用《孤独摇滚！》的角色、名称、场景、美术、音乐或台词。只吸收“安静而独立、用细节表达关心”的情绪质地。

## 3. 首次创建

首次进入只要求两步，避免把陪伴体验变成问卷。

1. 选择关系前史；
2. 选择城市，或选择“随机”。

随机只从四个预设城市中抽取。创建后城市和关系前史写入存档，正常使用时不可改；用户只有通过“重新开始一段新的故事”才会重新初始化。

| 关系前史 | 合理的人生版本示例 | 对话起点 |
| --- | --- | --- |
| 陌生网友 | 洛杉矶/伦敦读研或初入职场 | 正在试探地交换生活片段 |
| 高中同学 | 上海大学生 | 毕业后在不同大学重新联系 |
| 前同事 | 城市白领或转行者 | 不在同一家公司后的偶尔问候 |
| 久未联系的朋友 | 成都独立音乐相关工作者 | 熟悉感仍在，但共同细节已模糊 |

同一个核心人格在不同初始化中拥有不同人生，而不是生成不同的“换皮角色”。

## 4. 人物与关系引擎

### 4.1 三层角色契约

| 层级 | 作者文件 | 作用 | 是否随初始化变化 |
| --- | --- | --- | --- |
| 核心灵魂 | `Soul-core.md` | 性格、语言节奏、价值观、边界、喜好、关心方式 | 否 |
| 平行人生 | `Profile.md` | 城市、身份、作息、住处、关系前史、固定地点 | 是 |
| 当下生活 | `life-context.md` | 近期旅行、出差、同事合作、朋友见面、余波 | 持续更新 |

`Soul-core.md` 应表现为：安静独立、有审美和原则；不讨好、不无故热情；熟悉后以具体细节表达关心；偶尔说出直击要害的话；有自己的生活边界。它不能复制任何现有 IP 的外形、履历、口头禅或台词。

### 4.2 关系记忆

运行时不把 Markdown 全量当作聊天上下文。Markdown 是创作契约；实际状态以 `clientCloud` 中的 JSON 保存：

| 数据 | 内容 | 保留规则 |
| --- | --- | --- |
| `relationship` | 前史、称呼、熟悉度、信任、距离感、近期情绪 | 内部使用，不向用户展示数值 |
| `interaction_log` | 会改变以后行为的互动摘要 | 最多保留最近 20 条 + 长期摘要 |
| `shared_memories` | 承诺、习惯、重要选择、共同笑点 | 长期保留，用户可重置 |
| `life_context` | 她与朋友、同事、上司及生活计划的近期状态 | 可自然淡出，不要求结局 |

关系的变化只能由对话与事件造成。用户不点击“+10 好感”；系统应把行为变化呈现为她更愿意分享、主动联系或记得更多细节。

### 4.3 开放生活上下文

`life-context.md` 不保存“未完成主线”，只保存生活在继续发生的证据。例如：

- 她周五和闺蜜去海边；
- 她与同事共同赶一个项目；
- 上周旅行回来后仍常提到一家小店；
- 她和上司有一次不愉快，后来被新的日常慢慢覆盖。

一条上下文可以持续、淡出或在未来重现；没有“完成任务”或“故事收束”。朋友、同事、上司和随机路人均为场外人物，不做独立可聊天 NPC。

## 5. 真实时间与可用性

### 5.1 时间状态

```
设备当前时间 + 用户时区
        + 角色城市 IANA 时区
        + 当地日期与季节
        + 城市 + 当日日期的固定随机种子
        + 她的作息 / 生活上下文
→ 角色当地时间、天气、地点、可用性、事件候选
```

季节取角色城市的当地日期。天气不调用实时服务，而由 `city_id + YYYY-MM-DD` 的种子确定，且全天一致；它只在晴、阴、雨、风等低风险状态之间变化。

### 5.2 可用性状态

| 内部状态 | 可能地点 | 聊天行为 |
| --- | --- | --- |
| 空闲 | 公寓、咖啡馆 | 通常较快回复，可连续交流 |
| 碎片时间 | 通勤、排队、午休 | 回复较短，可能间隔数分钟 |
| 忙碌 | 上课、工作、与朋友见面 | 消息排队，事后带着经历回复 |
| 离线 | 睡眠或私人时间 | 不显示假在线；醒来/空闲后回复 |

用户的消息永不丢失。角色不能永久无故沉默；离线和忙碌状态都应在可控时间窗内生成可解释的后续回复。PoC 演示可在开发者调试入口加速时间，但对普通用户不暴露“快进剧情”按钮。

### 5.3 事件生成规则

事件生成器先选事实，后写文案：

1. 根据时间、天气、作息、关系与 `life_context` 选一个有限事件模板；
2. 写入事件 ID、时间戳、场景、涉及人物和情绪结果；
3. 由角色契约把事实转成聊天回复或短日记；
4. 更新关系和记忆摘要。

首轮模板包括：去咖啡馆、下课/下班、通勤、和朋友见面、项目压力、短途出行、独处休息。每次离线重入只交付一条最有意义的事件摘要，不能按小时堆积几十条。

生成失败时，使用同一事件模板的确定性保底文案，确保“回来时有回应”这个核心体验不依赖一次 LLM 成功。

## 6. 聊天与 3D 状态窗口

### 6.1 界面层级

```text
顶部：城市名、她的当地时间、含蓄状态描述
中部：固定镜头 3D 状态窗口（角色 + 当前地点）
下部：主聊天流与消息输入
```

状态不使用“在线/离线”绿点。使用可读的生活描述，例如“伦敦 · 22:14 · 回到公寓了”或“洛杉矶 · 18:20 · 还在外面”。聊天是主要操作；3D 窗口只需要展示，不要求自由移动。

### 6.2 场景组合

每座城市不建完整地图，而是由同一套四类镜头场景复用：

| 场景 | 城市差异 | 角色行为 |
| --- | --- | --- |
| 公寓 | 窗外天际线、陈设、色温 | 看书、煮咖啡、整理桌面 |
| 咖啡馆 | 菜单/店面、窗景、环境声 | 写作、发呆、等朋友 |
| 通勤 | 车窗、站牌、雨具、灯光 | 走路、等车、短暂查看消息 |
| 休闲地点 | 公园、海边、演出空间等 | 朋友聚会、散步、独处 |

上海体现通勤与雨天公寓；成都体现茶馆、社区和夜宵；洛杉矶体现黄昏、Live House 与暖色公寓；伦敦体现阴天、旧街区和独立文化空间。

## 7. 平台工作流与边界

### 7.1 Tripo Studio：角色和可交互小物件

使用网页会员完成构建期资产创作，不把 API key 或模型生成暴露给最终用户。

- 角色：用文本/参考图生成原创低模角色，迭代后导出 GLB；
- 动作：如网页工作区可用，完成绑定并只保留 `idle`、`sit/phone`、`walk` 等 PoC 必需动作；
- 道具：咖啡杯、唱片、背包、书、台灯等独立小件；
- 导入 Maker 前控制角色与单件道具面数，目标每件不超过 5,000 faces，并实机测帧率。

Tripo 官方资料确认可从文本、单图和多视图生成模型，开发者工作流能下载 GLB；其新开发者文档同时列出绑定、重定向与格式转换能力。Studio 会员与 API 权益是否互通不能假设，PoC 以网页导出为准。

### 7.2 Marble：地点气质、镜头与环境参考

Marble 网页会员用于生成四城的“空间母版”：公寓、咖啡馆、通勤和休闲地点。优先使用文本、概念图或多图来稳定镜头与风格。

**首选落地方式：** 将 Marble 生成的 360 全景、缩略图或录制的短镜头作为 Maker 3D 状态窗的背景/远景，并在前景放置 Tripo 角色和少量低模道具。

**不要把 Marble 高质量 GLB 直接作为移动端主场景。** 官方规格中，高质量网格约 60 万至 100 万三角面，生成可达约一小时且每用户每小时有限流；Collider GLB 也约 10–20 万三角面。它们适合作为概念、镜头、远景和少量离线预渲染资产；若尝试导入 Maker，必须先做单场景真机性能 Spike。Marble 的世界合成、镜头录制和浏览器分享可直接服务于视觉看板和 1–2 分钟 walkthrough。

### 7.3 TapTap Maker：运行时与发布

TapTap Maker 是唯一运行时：聊天 UI、Lua 状态机、`clientCloud` 存档、GLB 导入、预览与真机二维码测试都由它承担。

- 角色与低模道具放入 `assets/`；
- Lua 负责时区换算、状态选择、事件去重和存档；
- Maker AI（若实测可用）只负责把已选事实润色成角色对话；
- `clientCloud` 保存单人关系数据；WASM 预览刷新会丢内存，因此记忆与离线事件必须在真机测试验证；
- 发布前完成图标、截图、封面、简介、开发者的话与实机视频。

Maker 能否在当前项目中直接使用 Marble 的全景格式、复杂 GLB 动画与具体 Lua API 名称，均是实施前必须验证的集成点；不可把历史文档中的推测 API 当作已验收事实。

### 7.4 资产数据流

```text
原创角色概念 → Tripo Studio → GLB / 低模道具
城市空间提示词 → Marble Web → 全景 / 镜头 / 环境参考
                         ↓
Tripo 前景角色 + Maker 低模场景 + Marble 背景远景
                         ↓
TapTap Maker（聊天 UI、Lua、clientCloud、真机测试、发布）
```

## 8. 技术架构

```text
TapTap Maker 客户端
├─ Chat UI：消息、排队态、状态描述
├─ StatusScene：固定机位、角色动画、背景与环境音
├─ TimeService：设备时区 → 角色当地时间、季节、天气种子
├─ AvailabilityService：作息 → 空闲/碎片/忙碌/离线
├─ EventService：选择模板、记录事件、保底文案
├─ MemoryService：clientCloud JSON 读写、摘要与上限
└─ ContentService：Soul/Profile/关系上下文 → Maker AI 文案（可降级）
```

职责边界：Lua 决定事实与时机；生成式文本不能篡改事件事实、地点或时间。运行时不调用 Tripo 或 Marble。

## 9. 最小可行 PoC 与验收

### M0：平台与资产 Spike

- 用 Tripo Studio 导出一个原创角色 GLB；
- 在 Maker 导入并显示；
- 用 Marble 生成一个咖啡馆环境母版，选择全景/录制镜头作为背景；
- 在真实手机上验证加载、清晰度与帧率。

**通过条件：** 一个可见角色在带城市氛围的状态窗口里稳定运行。

### M1：时间和状态

- 只支持“陌生网友 × 洛杉矶”；
- 根据角色当地时间显示至少早晨、傍晚、深夜三种状态；
- 消息在“忙碌/睡眠”中排队，恢复后给出可解释回复。

**通过条件：** 同一条用户消息在不同角色当地时段会得到不同的状态、场景和回复时机。

### M2：关系持续性

- 保存关系前史、一次关键互动和一条生活上下文；
- 下一轮回复准确回调一项共同记忆；
- LLM 不可用时仍使用模板完成回应。

**通过条件：** 重启或真机重进后，记忆仍然存在且不重复生成同一事件。

### M3：四城初始化

- 开放上海、成都、洛杉矶、伦敦与“随机”；
- 每城至少有两种可见状态窗，并验证当地时区切换；
- 高中同学、久未联系朋友各做一个可演示的档案组合。

**通过条件：** 城市改变会同时改变时差、生活身份、场景词汇和事件模板。

### M4：提交物

- 真机二维码 / 可玩 Demo；
- 1–2 分钟 walkthrough：北京时间发消息 → 她在异地忙碌 → 状态窗变化 → 带经历回复 → 记忆回调；
- 至少三张视觉资产：角色特写、异地傍晚状态窗、延迟回复后的生活事件；
- 记录 Tripo 与 Marble 的生成、导出和接入过程，证明工具贡献。

## 10. 风险与回退

| 风险 | 回退 |
| --- | --- |
| Maker AI 角色扮演不稳定 | 事件事实由 Lua 固定；用模板文案与短句兜底 |
| Marble 网格或 splat 无法高效接入 Maker | 用 Marble 全景/短镜头做背景，Maker 仅渲染低模前景 |
| Tripo 角色无法直接播放所需动作 | 先用 idle + 相机/表情/气泡营造状态；动作作为增量 |
| `clientCloud` 或离线时间异常 | 本地内存保底并提供“重新整理记忆”，不清空用户历史 |
| 角色长时间不回造成挫败 | 给出含蓄状态描述，设定最大回复窗口并保证后续解释 |
| 城市太多导致资产碎片化 | M1 先锁洛杉矶，M3 后再扩到四城 |

## 11. 验收优先级

必须按此顺序推进，前项不通过不进入下一项：

1. Maker 真机能加载角色与状态窗；
2. 本地时间与角色城市时间计算正确；
3. 消息排队与延迟回复可演示；
4. 重进后共同记忆和事件去重正确；
5. 四城差异、视觉打磨和提交物完整。

## 12. 研究依据（2026-09-15 核验）

- [Tripo Studio](https://studio.tripo3d.ai/)：网页 3D Workspace，首页展示图像生成 3D 与资产工作流。
- [Tripo Developers — Quick Start](https://developers.tripo3d.ai/en/docs/quick-start)：文本到模型任务完成后可下载 GLB；文档亦列出游戏角色相关工作流。
- [Tripo Developers — Introduction](https://developers.tripo3d.ai/en/docs/introduction)：当前开发者能力包含文/图/多视图建模、贴图、格式转换、网格处理、绑定与动作重定向。
- [TapTap 制造 Skills](https://maker.taptap.cn/skills)：确认其定位为 AI 游戏创作工具，并展示 UrhoX Lua、3D 场景资产管线等现行 Skill。
- [Marble 官方文档概览](https://docs.worldlabs.ai/)：文本、图片、多图、视频与粗 3D 结构生成世界，以及 Studio 合成、镜头录制、导出能力。
- [Marble 导出规格](https://docs.worldlabs.ai/marble/export/specs)：360 全景为 2560×1280；Collider GLB 约 10–20 万三角面；高质量 GLB 约 60–100 万三角面并有生成时长/限流约束。

> 本规格将旧版“三位 NPC 自动小镇”替换为“一位平行时空聊天对象 + 3D 状态窗”。旧文档保留为历史方案，在实施时不得混用其角色、事件和 UI 契约。
